# Rabbit Hole в StarOS Mini: статический разбор

29.10.2026. Объект: `/vendor/staros/box` из дампа StarOS 1.82.7, ARM ELF32.
Это анализ чужого старого дампа, а не проверка работающей версии 1.103.x.

## Краткий результат

Найден и дизассемблирован действительный код JWT-авторизации и его связь с AdbService.
Простой команды «включить root», принимаемой без авторизации, в исследованной цепочке нет.
Проверка использует RS256, поля устройства и UUID сессии. После неё вызывается callback включения ADB.
Этот callback не снимает ограничения загрузчика и не меняет kernel cmdline.

> Отдельно: в SberCast-маршруте найден другой ADB-вход — `StarMessage` case 115
> по смещению 0x18 с проверкой пароля PBKDF2-HMAC-SHA256 (1000 итераций,
> 32 байта). Это не JWT и не `configHash`; по star-command маршруту он
> недостижим. Детали и границы — в [SBERCAST-ROUTING.md](SBERCAST-ROUTING.md).

## Проверенная цепочка вызовов

Адреса ниже — **виртуальные адреса ELF**, не смещения исходного NAND-дампа.

1. `0x0012b65c`: разбор protobuf-запроса и dispatch по значению action (ветки 0 и 1).
2. `0x0012b5a8`: ветка ADB, вызывает `0x0012d670`; результат преобразуется в код ответа.
3. `0x0012d670`: проверка credentials, UUID, device/product, уровня `adb_root`, вызов callback.
4. `0x0012d0c8`: `staros::RabbitHole::parseJwtToken`, имя подтверждается собственной диагностикой функции.
5. Callback из `AdbServiceImpl::init` на `0x0012aba8` указывает на thunk `0x00127ed4` -> `0x00127d54`.
6. `0x00127d54`: `staros::AdbServiceImpl::enableAdb()`, запускает `enableAdbCommand` через `0x00127ae0`.

## JWT

`parseJwtToken` создаёт валидатор с фиксированным именем `RS256` и SHA-256 (`EVP_sha256`), передаёт сохранённый объектом ключ по смещению `this+0x44`.
Конструктор RSA-валидатора: `0x004d5c04`; разбор токена через `0x004d46b0` -> `0x004d413c`.

Из тела JWT извлекаются:

```text
device.serialNumber
device.product
sessionUUID
levels
```

`0x0012d670` затем:

- при неуспешном parseJwtToken возвращает отказ;
- получает текущий UUID через `0x0012c070`;
- сравнивает sessionUUID с текущим UUID;
- сравнивает serialNumber и product с сохранёнными свойствами устройства;
- ищет `adb_root` в наборе levels;
- только после этих проверок вызывает callback `this+0x40`.

Это реконструкция потока управления, а не возможность самостоятельно выпустить валидный токен.
Чтение открытого ключа не даёт закрытого ключа подписи.
Отсутствие/наличие отдельных стандартных JWT-проверок (`exp`, `aud`, `iss` и т.п.) в полном валидаторе ещё не установлено; утверждать их обход нельзя.

## Криптографическая проверка

- GOT-запись `0x0072a1d4` указывает на vtable `0x0070faa4`.
- Ветка валидатора использует метод `0x004d58b8`.
- В этом методе видны `EVP_MD_CTX_new`, `EVP_DigestInit_ex`, `EVP_DigestUpdate`, `EVP_VerifyFinal`.
- Успех возвращается только если `EVP_VerifyFinal` вернул 1.
- Код разбора формата JWT и обработки исключений также присутствует; это не просто поиск слов RS256 в бинарнике.
- Полный аудит JWT-библиотеки и динамическое тестирование не выполнены. Уязвимость не установлена.

## UUID сессии

`0x0012c070` использует steady_clock и интервал в миллисекундах для обновления UUID.
В init для `uuidLifetimeMs` передаётся default `0x0036ee80` = 3 600 000 мс (1 час).
Фактическое значение может быть изменено конфигурацией; текущая конфигурация колонки не считана.
Не следует считать UUID бессрочным или равным UART challenge.

## Почему это пока не путь к root на Linux Mini

После JWT-проверки код не запускает shell напрямую: вызывается AdbService.enableAdb().
Она читает `adb.enableAdbCommand` из конфигурации и исполняет полученную команду.

В извлечённом star.json:

```text
enableAdbCommand = /vendor/staros/enable_adb.sh
disableAdbCommand = /vendor/staros/disable_adb.sh
```

В списке 1242 записей SquashFS этих скриптов нет (включая ссылки).
Возможность их появления через другой компонент/overlay или runtime config не проверена.
Поэтому наличие общей сервисной реализации не гарантирует работоспособность этой цепочки на Linux Mini.

Отдельно `/etc/init.d/S89usbgadget` проверяет разрешение в kernel cmdline до создания USB ADB.
Изменение user setting или успешный общий StarOS callback само по себе не добавляет `androidboot.rabbith.adb_root=true` к уже запущенному ядру.

## Две разные границы доступа

1. Загрузчик: UART `RABBIT HOLE v2`, формирование bootargs, разрешения Linux console/ADB.
2. Пользовательский StarOS: protobuf RabbitHoleRequest, JWT, callback AdbService.

Тождество протоколов, ключей и форматов ответов не установлено.
Не отправлять JWT в UART только из-за совпадения названия.

## Метод и ограничения

- Использованы Capstone и pyelftools из PyPI в локальном окружении.
- ELF stripped: динамические символы не содержат имён RabbitHole/AdbService.
- Границы функций восстановлены по 17 156 записям `.ARM.exidx`.
- Xref найдены через ARM PC-relative literal load + ADD PC, а также буквальные указатели и MOVW/MOVT.
- `reverse.py` сохраняет выбранные функции в `reverse/function-*.asm`.
- Автоматические аннотации literal могут показывать случайный текст для относительного смещения/GOT; достоверные выводы проверялись по последовательности инструкций. Это не полноценный декомпилятор.
- Образ прошивки не исполнялся. Сеть колонки, авторизация, USB и UART не менялись.

## Следующий обоснованный шаг

Для проверки применимости нужен актуальный `box`/OTA текущей версии или действительные исходники соответствующего загрузчика.
Можно отдельно исследовать read-only запрос информации RabbitHole в текущем локальном API, но транспорт и доступность обработчика сначала надо подтвердить. После factory reset прежнее сопряжение нельзя считать действующим.
Прямой работоспособный способ включения shell/root этим этапом не получен.
